Creating a Micro EC2 Bastion (Amazon Linux 2023)

A tiny, SSM-managed EC2 instance used as a bastion for RDS tunneling, S3 access, and internal resource access. No SSH keys, no public IP, no open ports.

1Create the IAM Role for the Bastion

The bastion needs an instance profile with policies for SSM, RDS connectivity, and S3.

# Create the trust policy
cat <<'EOF' > bastion-trust.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "ec2.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}
EOF

# Create the role
aws iam create-role \
  --role-name bastion-ssm-role \
  --assume-role-policy-document file://bastion-trust.json

# Attach SSM managed policy
aws iam attach-role-policy \
  --role-name bastion-ssm-role \
  --policy-arn arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore

# Create instance profile and add role
aws iam create-instance-profile \
  --instance-profile-name bastion-ssm-profile

aws iam add-role-to-instance-profile \
  --instance-profile-name bastion-ssm-profile \
  --role-name bastion-ssm-role

2Launch the Bastion Instance

# Find the latest AL2023 AMI
AMI_ID=$(aws ssm get-parameter \
  --name "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64" \
  --query "Parameter.Value" --output text)

# Launch t3.micro (or t3.nano for even smaller)
aws ec2 run-instances \
  --image-id $AMI_ID \
  --instance-type t3.micro \
  --iam-instance-profile Name=bastion-ssm-profile \
  --subnet-id subnet-0abc123def456 \
  --security-group-ids sg-0abc123def456 \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=bastion-ssm}]' \
  --metadata-options HttpTokens=required \
  --no-associate-public-ip-address \
  --count 1
Key flags:
  • --no-associate-public-ip-address — no public IP, SSM connects via VPC endpoints or NAT
  • --metadata-options HttpTokens=required — enforces IMDSv2 (SOC2 requirement)
  • No --key-name — no SSH keys needed, access is exclusively via SSM

3Attach Additional Policies

For RDS tunneling, the bastion itself doesn't need RDS IAM policies — it connects via standard TCP to the RDS endpoint within the VPC. The security group rules handle access.

For S3 access from the bastion:

# Create an inline policy for scoped S3 access
cat <<'EOF' > bastion-s3-policy.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:ListBucket",
      "s3:PutObject"
    ],
    "Resource": [
      "arn:aws:s3:::my-bucket",
      "arn:aws:s3:::my-bucket/*"
    ]
  }]
}
EOF

aws iam put-role-policy \
  --role-name bastion-ssm-role \
  --policy-name bastion-s3-access \
  --policy-document file://bastion-s3-policy.json

4Verify SSM Agent

Amazon Linux 2023 comes with SSM Agent pre-installed. Verify it's running:

# Check that the instance appears in SSM
aws ssm describe-instance-information \
  --filters "Key=InstanceIds,Values=i-0abc123def456" \
  --query "InstanceInformationList[0].{Id:InstanceId,Status:PingStatus,Agent:AgentVersion}"

Expected output shows PingStatus: Online. If the instance doesn't appear:

  • Verify the IAM role has AmazonSSMManagedInstanceCore
  • Verify the subnet has a route to SSM endpoints (NAT gateway or VPC endpoints)
  • Wait 2-3 minutes after launch for the agent to register

5Connect via SSM

# Start a session
aws ssm start-session \
  --target i-0abc123def456 \
  --profile my-dev
▶ Identity Policies

Your SSO identity (the human user) needs these permissions to use SSM and manage the bastion:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ssm:StartSession",
        "ssm:TerminateSession",
        "ssm:ResumeSession",
        "ssm:DescribeSessions"
      ],
      "Resource": [
        "arn:aws:ec2:*:*:instance/i-0abc123def456",
        "arn:aws:ssm:*:*:document/AWS-StartSSHSession",
        "arn:aws:ssm:*:*:document/AWS-StartPortForwardingSessionToRemoteHost"
      ]
    },
    {
      "Effect": "Allow",
      "Action": [
        "ec2:DescribeInstances"
      ],
      "Resource": "*"
    }
  ]
}
▶ EC2 Role Policies

The EC2 instance role (bastion-ssm-role) needs:

  • Required: AmazonSSMManagedInstanceCore — allows SSM Agent to communicate with the SSM service
  • Optional: Scoped S3 access via inline policy (only the buckets you need)
  • Not needed: RDS IAM policies for standard password-based RDS connections (the bastion just forwards TCP)

Minimum role policy summary:

Managed: AmazonSSMManagedInstanceCore
Inline:  s3:GetObject, s3:ListBucket, s3:PutObject
         (scoped to specific bucket ARNs)
▶ VPC, Subnet, and Security Group Requirements

Subnet

Place the bastion in a private subnet with a route to:

  • A NAT Gateway (for SSM endpoint connectivity), OR
  • VPC Endpoints for ssm, ssmmessages, and ec2messages

VPC Endpoints are preferred — they keep traffic off the internet entirely.

Security Group — Bastion

  • Inbound: No rules needed (SSM initiates outbound)
  • Outbound: HTTPS (443) to SSM endpoints, plus TCP to RDS port (3306/5432) within the VPC

Security Group — RDS

  • Inbound: Allow TCP on the database port from the bastion's security group
# Allow bastion to reach RDS on port 3306 (MariaDB/MySQL)
aws ec2 authorize-security-group-ingress \
  --group-id sg-rds-group-id \
  --protocol tcp \
  --port 3306 \
  --source-group sg-bastion-group-id
▶ SOC2-Friendly Reasoning

This bastion design satisfies several SOC2 controls:

  • No SSH keys: Eliminates key management and rotation requirements
  • No public IP: Instance is not directly reachable from the internet
  • IMDSv2 enforced: Prevents SSRF-based credential theft
  • SSM session logging: All sessions are logged to CloudTrail; optionally log to S3/CloudWatch
  • Identity-based access: Who connects is tied to their SSO identity, not a shared key
  • Least privilege: Bastion role has only SSM + scoped S3; no admin access
  • No inbound ports: Security group has zero inbound rules

Enable SSM session logging for audit trails:

# In SSM → Session Manager → Preferences:
# - Enable S3 logging (encrypted bucket)
# - Enable CloudWatch logging
# - Enable KMS encryption for sessions
